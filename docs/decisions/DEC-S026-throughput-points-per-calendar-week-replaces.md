## DEC-S026: Throughput (points per calendar week) replaces transcript-based active-time velocity (supersedes DEC-S024)

**Decision:** Velocity is **throughput — points shipped per calendar week — computed from GitHub issue `closedAt` dates + `points:N` labels.** The transcript-dependent `active = wall − breaks` model (DEC-S024) is retired entirely, along with break inference, `wall_clock / point`, and any `active_time`. hrs/pt was secretly doing two jobs — forecasting and estimate calibration — and neither needs the transcript: forecasting → throughput; calibration → a per-task re-estimate tally at retro. `wall_clock` survives only as the `/its-dead` on-screen gut-check, never quoted as a velocity.

**Why:** DEC-S024's own skill set `total_breaks_hours = 0` whenever the transcript was unreadable, which makes `active = wall_clock` — overnight gaps and all — i.e. the `wall/pt` number the guide forbids. Transcripts live on inaccessible paths for ~every web/Desktop session, so the headline degraded to the forbidden number as the *normal* case, not the edge. Three rebuilds (DEC-S013 → S015 → S024) all stayed inside "reconstruct keyboard hours" and all died on the same root cause. The metric, not the formula, was wrong for a solo+Claude shop: Claude does the labor, so effort-hours aren't the scarce quantity — calendar clearance rate and estimate stability are. Dates + labels live in GitHub forever, so throughput is measurable on every repo *and* reconstructable retroactively.

**Validated before committing (2026-06-11, against bushel/crewbook/muster/helm):** throughput reads cleanly off pure GitHub data — bushel recomputed 222 pts across 5 weeks with no transcript. But two findings reshaped the headline:
- **The fleet is burst-shaped.** Every project is a 1–6 week sprint then done/maintenance (bushel 5 wk, muster 2, crewbook 3, helm 3, sailbook a 10-day burst). Nothing produces a calendar *trail*, so a trailing rolling-window band — the first design — collapsed to ≤2 overlapping windows dominated by one spike week. **Headline is therefore a lifetime rate, not a trailing trend:** points / calendar-week (realized pace, incl. idle weeks) and points / active-week (intensity when shipping). A rolling band is shown only when a repo has ≥2×window weeks of history.
- **Per-phase rate explodes on sub-week phases.** Solo phases close in 0.0–0.7 weeks; dividing points by a sub-week denominator yields nonsense (muster phase:4 = 516 pts/wk from 1 pt). So a phase rate is quoted only when the phase spans ≥7 days; shorter phases are recorded as `burst — N pts over Dd`.
- **PR open→merge is merge latency, not build effort.** A by-point-size cycle-time view was built and tried as a "when's it done?" forecast; on bushel it came back flat (2/3/5-pt PRs all merge in ~minutes, p85 ~6–8h). Structural, not noise: the PR opens *after* the build is done, so open→merge can't see effort, and the build-time timestamp that *would* scale (issue `createdAt`) is batch-stamped at phase start, unusable. Kept as a relabeled **flow-health** stat (do PRs sit?), demoted from forecasting. The estimation signal that *did* validate is **pointing stability** — pts/issue held a tight 2.29–3.60 across bushel's 9 phases.

**Merge dates only — never re-pair PR-open → PR-merge.** That window math is exactly DEC-S024's bug. Dates are not windows; they can't sum past wall-clock or assume merge ordering. Cycle time (below) uses each PR's *own* open→merge span and only reports the distribution — it never sums spans across PRs.

**What changes:**
- **This slice (landed):** `/retro` Step 2 fully rewritten (throughput + estimate-calibration tally; no transcript) in **both** skill copies — the template (`dev/claude/skills/retro/SKILL.md`) and seeds' dogfooded live install (`.claude/skills/retro/SKILL.md`), which had drifted onto the older DEC-S015 model and is now reconverged byte-identical. Downstream Steps 3/4/5.5/6/7/8/10 + Notes updated off active/breaks. `velocity.py` → `throughput.py`: reads GitHub (issue dates+labels, merged PRs) instead of RETROSPECTIVES.md; reports the two lifetime rates, per-phase points + pointing-stability (pts/issue) + span, and **PR merge latency (open→merge)** as a median/p85 in hours — a flow-health signal — plus a drift-proof issue-count companion via `--issues`.
- **Deferred (separate task):** `VELOCITY_AND_POKER_GUIDE.md` Part 1 rewrite (Part 2 poker untouched); `RETROSPECTIVES.md` + `PROJECT_PLAN.md` velocity-table column swap (`Wall/Breaks/Active/h-pt` → `Points/Span/Throughput/Re-est'd/Net-drift`), historical blocks frozen; the `seeds-version` edit + SCHEMA_VERSIONS entry if the schema call changes.

**Historical retros stay as written** (DEC-S024 precedent). Phases closed under the old model keep their retired columns; `throughput.py` recomputes from GitHub and is independent of old retro prose, so history needs no backfill — it recomputes wherever the `points:N` labels reach.

**Honest limits (named, not hidden):** throughput is capacity *including availability* — a slow week and an off week look identical; correct for "when does it ship," never quote it as at-keyboard speed. It is retroactive only as far back as the `points:N` labelling ritual — a project predating the labels is invisible (sailbook returns nothing; the same blind spot hrs/pt had). And it is even more project-shape-specific than hrs/pt: never forecast a new project from another's throughput.

**Schema:** additive within **v4** — session frontmatter is unchanged (`/its-dead` writes no time fields), and the retro skill is a logic-class file whose behavior change touches no cross-file contract `/pull-seeds` enforces. No version bump, consistent with DEC-S024 on a directly comparable retro-Step-2 change (and DEC-S023/S025). The trigger list nominally flags retro-contract + table-column changes for a bump; this is Eric's call, recorded here as no-bump. If the deferred doc/table sweep revises that judgment, it carries the `seeds-version` edit + SCHEMA_VERSIONS entry.

**Alternatives considered:** patch the break inference a fourth time (rejected — three rebuilds is the tell the metric is wrong, not the formula). Keep hrs/pt and add throughput alongside (rejected — two velocities, one unmeasurable, is the noise DEC-S024 already cut). Trailing rolling-window band as the headline (rejected after validation — the burst-shaped fleet has no trail to roll over). Reconstruct sailbook's pre-label history from the session-log archive (rejected — feasible but a separate one-off, and validation proved sailbook was itself a 10-day burst, so it adds no steady-state signal).
