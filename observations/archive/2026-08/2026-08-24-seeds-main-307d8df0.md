## Candidate — `settings-policy.mjs` silently misreads a settings-file path as a repo root

**What happened:** Two exploratory sweeps across 11 sibling repos (lines 94,
98) invoked `node dev/claude/scripts/settings-policy.mjs "$p"` and
`settings-policy.mjs "$p"` where `$p` was a full path to a `settings.json`
*file* (e.g. `/home/estoffer/helm/.claude/settings.json`), passed as a bare
positional argument with no `--repo`/`--all`/`--seeds` flag. Both sweeps
returned plausible-looking `current`/`STALE`/`ABSENT` output for every repo
with no error. The assistant then noticed the results didn't match what the
Step 8.6 briefing had already established (line 110: *"My sibling sweep
measured nothing — a bare positional is a repo root, not a settings path
(`settings-policy.mjs:107`), so every one of those runs re-checked
`~/.claude/settings.json`"*), grepped the script's own arg-parsing (line
102), and re-ran the sweep correctly with `--repo` (line 111) and again for
one repo in detail (line 115) before the real 5-file table could be
assembled. Confirmed by reading the script directly:
`dev/claude/scripts/settings-policy.mjs:107` —
`const repoRoot = resolve(positional[0] ?? process.cwd())` — treats *any*
bare positional as a directory to resolve as repo root, and with no mode
flag set, the check ran against the wrong target and printed a normal-looking
result instead of erroring. The script's own docstring at lines 33–34
documents the two supported invocation shapes (`--repo [path]`, `--all
[path]`); neither shape is a bare settings.json file path, but nothing in the
script rejects one.

**Why it looks like a repeatable pattern, not a one-off:** this is a script
in `dev/claude/scripts/` invoked ad hoc, outside any skill step — Step 8.6
only documents `--all .` for the current repo. Any future session doing the
same kind of exploratory multi-repo sweep (which this session's task
explicitly invited: "you should find 5 files out of sync") is equally likely
to reach for a positional file path first, since that's the natural shape
for "check this file" and the script accepts it without complaint.

**Cost if it recurs:** two full 11-repo sweeps' worth of wasted tool calls
and context (roughly 3 extra Bash round trips here); recoverable, and no
wrong data reached the operator — the assistant caught the discrepancy
itself before presenting the briefing. On a less careful pass, though, the
false "current"/"STALE" readings could have been reported as fact, since
nothing about the tool's output flags itself as checking the wrong target.

**Self-announcing:** no. Both bad sweeps returned normal-shaped output
(`current`, `STALE`, `ABSENT` per repo) with no error, warning, or exit
