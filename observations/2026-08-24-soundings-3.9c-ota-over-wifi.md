## Candidate B — ESP32 serial port opened without clearing DTR/RTS silently re-enters the bootloader

**What happened:** `gateway/tools/bench_reply.py` (new file this session, `Write` at line 818) opens `/dev/ttyUSB0` to run the downlink measurement. The project deliberately avoids pyserial (`ModuleNotFoundError: No module named 'serial'` at line 800 confirms it isn't installed; the design explicitly uses structural `ByteStream`/`WritableStream` protocols instead, per message 34 in the assistant-text sweep). Opening the port — via whatever mechanism `open_port()` used before the fix — asserted DTR and RTS, which on the Heltec board's USB-serial bridge holds GPIO0 low through reset: the ESP32 dropped into its ROM bootloader and never ran the application. Diagnosis (lines 895-936): zero bytes over 75s despite the node transmitting 3 times → confirmed the board itself was fine (`stty raw` + `cat` on the same port worked) → 385 reads all empty with VTIME behaving correctly, ruling out a termios misconfiguration → the tell was that Python never even received the boot banner Claude had *just* added to the gateway sketch for an unrelated reason → recognized as the classic DTR/RTS-into-bootloader trap and confirmed by clearing the lines. Cost, in the assistant's own words (line ~ message 45): *"invisible to every host test, and only a physical board could show it... the kind of thing that costs a whole bench session."*

**Cost if it recurs:** a lost bench session (the project's own stated unit of cost for this class of bug — matches "Guessing a third-party unit (RadioLib timeout ms vs µs) cost a bench session" from the session-open briefing, a distinct prior incident of the same shape: a serial/radio boundary assumption that only a physical board exposes).

**Self-announcing:** no. The symptom (silence on the port) is identical to "radio failed to start," "cable unplugged," or "daemon never sent," and the transcript shows Claude initially pursuing the wrong branch (checking whether the board was relaying at all) before isolating the actual cause.

**Cause:** nothing in the project's docs names this ESP32-specific gotcha. `.claude/CLAUDE-context.md` has no `## Workflow Notes (project)` section at all — the shell (`CLAUDE.md:219`) names that as the place project-specific "dev-server checks, stale-process traps" belong, and it's currently empty in this project, so there was no prior warning to consult. This is a first occurrence, not a repeat within this transcript, but it is the same *shape* of failure the project has already paid for once (the RadioLib units bug from session 8, referenced in this session's own opening briefing) — an unverified assumption at a hardware/library boundary, invisible to every host test.

**Operator reaction:** none — the user was not present for this diagnosis; it happened inside a single build-handback turn and was reported, not escalated on.

**Sketch (proposed, not a rule):** a documented gotcha — "opening a board's serial port from Python must explicitly clear DTR/RTS (or open via a mechanism that doesn't assert them) or the ESP32 re-enters its bootloader silently" — belongs in the project's `## Workflow Notes (project)` slot once that section exists, alongside the RadioLib units note. Whether it's worth promoting past this one project (it would apply to `tinkle`, the sibling ESP32 project, too) is `@workout`'s call.
